10块钱发10个红包，抢完一算账，总金额9.99——少了一分钱。金额拆分的精度问题，只是抢红包的第一道坎。真正的难点在并发：2亿人同时抢，红包余额的扣减必须是原子的，还不能出现"两个人都抢到同一个金额"。这篇按"需求→难点→选型→代码→坑"拆一套能扛住红包雨的方案，重点讲清楚金额怎么拆、并发怎么抢、账怎么对平。

## 需求一句话：人人有份，还要拼手气
抢红包的需求拆开是四句话：发红包的人指定总金额和个数；每个红包金额随机，但所有红包加起来必须等于总金额；多人同时抢，同一红包不能被抢两次；没抢完的红包要退回。四句话里，第二句是金额拆分问题，第三句是并发问题，第四句是超时问题。面试官最常从第三句开始问，但第二句答不上来一样扣分。说实话我第一次写红包功能，就是栽在金额拆分上，被对账任务逮了个正着。

## 难点拆解：金额拆分和并发抢，两个坎
先看金额拆分。最常见的坑是"随机分"：每次都随机生成一个金额，最后一个兜底——结果前9个把10块都分完了，第10个只能拿0。或者反过来，前几个分太少，最后一个巨大无比。业界通用的解法是二倍均值法：每次从剩余金额里随机取一个值，上限是"剩余金额÷剩余个数×2"。

```
二倍均值法：10元 10个红包
第1个：剩余10元，10个 → 上限 10/10×2 = 2元，随机取 0~2，假设 1.5
第2个：剩余8.5元，9个 → 上限 8.5/9×2 ≈ 1.89，随机取 0~1.89，假设 1.2
第3个：剩余7.3元，8个 → 上限 7.3/8×2 ≈ 1.82，随机取 0~1.82，假设 0.8
...以此类推，最后一个是剩余全部
```

这个算法的精髓是：每次取的上限随剩余金额和个数动态变化，前几个不会分光，最后一个也有合理金额。平均下来每个红包金额在均值附近波动，既拼手气又不至于差距离谱。

再看不并发的坑。我一般会把这题和秒杀放一起对比着记，两者防超抢的思路是通的。抢红包的扣减和秒杀类似，也是"先查余额再扣"会超抢：两个请求同时查到红包还有钱，都扣，金额就负数了。但红包比秒杀多一层——它扣的不是整数库存，是金额，而且每个红包的金额都不同，所以不能用简单的`DECR`，得用Lua脚本在原子操作里"取一个金额→扣减→记录谁抢到"。

## 方案选型：金额预拆分 vs 抢时拆分
拆金额有两种时机，面试官喜欢让你对比。

方案A：抢之前把所有金额拆好存Redis。 发红包时一次性算好N个金额，存成Redis List。抢的时候`LPOP`弹出一个——单命令原子，天然不超抢，还特别快。缺点是发红包时要把N个金额都算出来，红包个数几万的话，拆分计算和存储有成本。

方案B：抢的时候边拆边扣（Lua原子）。 不预拆，抢的时候在Lua脚本里算本次金额并扣减。优点是发红包即时，不用等拆分；缺点是要写脚本，脚本里做浮点运算要小心精度。

我一般倾向方案A：金额预拆到Redis List，抢的时候`LPOP`，简单、快、不会错。只有红包个数特别大（比如百万级）才考虑方案B。这个取舍在面试里讲清楚，比背概念强。说白了，面试官要听的就是你踩过坑之后形成的判断。

## 核心代码：预拆金额 + LPOP 原子抢
方案A的核心就两段代码。我觉得这段代码是整个红包系统里最值得背熟的，面试手写基本就考它。发红包时拆分并存入Redis：

```java
// 发红包：二倍均值法拆分，存入 Redis List
public List<BigDecimal> splitRedPack(BigDecimal total, int count) {
    List<BigDecimal> amounts = new ArrayList<>();
    BigDecimal rest = total;
    int restCount = count;
    Random random = new Random();
    for (int i = 0; i < count - 1; i++) {
        // 二倍均值：上限 = 剩余金额 / 剩余个数 * 2
        BigDecimal max = rest.divide(BigDecimal.valueOf(restCount), 2, RoundingMode.DOWN)
                .multiply(BigDecimal.valueOf(2));
        BigDecimal amount = BigDecimal.valueOf(random.nextDouble())
                .multiply(max).setScale(2, RoundingMode.DOWN);
        if (amount.compareTo(BigDecimal.ZERO) == 0) {
            amount = new BigDecimal("0.01");   // 保底1分
        }
        amounts.add(amount);
        rest = rest.subtract(amount);
        restCount--;
    }
    amounts.add(rest);   // 最后一个拿剩余全部
    return amounts;
}
 
// 拆完塞进 Redis List，抢的时候 LPOP
public void preloadRedPack(String packId, List<BigDecimal> amounts) {
    List<String> values = amounts.stream().map(BigDecimal::toString).toList();
    redis.opsForList().rightPushAll("redpack:" + packId, values);
}
```
抢红包时`LPOP`弹出一个金额，单命令原子：

```java
// 抢红包：LPOP 原子弹出一个金额，天然不超抢
public BigDecimal grab(String packId, Long userId) {
    // 一人一单：同一用户不能重复抢
    Boolean first = redis.opsForSet().add("redpack:users:" + packId, userId.toString());
    if (!Boolean.TRUE.equals(first)) {
        return null;   // 已抢过
    }
    String amount = redis.opsForList().leftPop("redpack:" + packId);
    if (amount == null) {
        // 红包已抢完，回滚用户记录
        redis.opsForSet().remove("redpack:users:" + packId, userId.toString());
        return null;
    }
    // 异步入账：抢到金额记到用户余额，发MQ落账务流水
    mq.convertAndSend("redpack-account-topic",
            new RedPackGrabMsg(packId, userId, new BigDecimal(amount)));
    return new BigDecimal(amount);
}
```
两个关键点：`LPOP`是单命令原子操作，两个并发请求不可能弹出同一个金额；`SADD`判断一人一单，抢完的红包回滚用户记录。抢到金额后异步入账，账务流水走MQ，避免同步写库把抢红包的接口拖慢。

账务这块有个隐藏要求——最终一致性。抢红包是"先抢到、后入账"，用户看到的是"抢到了"，金额要异步进余额。如果入账失败，得靠对账任务补账，不能出现"用户抢到了但钱没到"。这个和秒杀的"Redis扣了DB没减"是同一类问题，解法也一样：消费重试 + 定时对账。

聊到这里顺便说下红包系统的整体架构。发红包是低频写（一个用户发一个），抢红包是高频读+写（几万人同时抢一个），所以红包的存储天然分成两层：热数据（正在被抢的红包）放Redis，冷数据（抢完的红包记录、账务流水）落MySQL。

Redis List存金额、Set存已抢用户、Hash存红包元信息；MySQL存红包主表、用户红包表、账务流水表。两层之间靠MQ异步同步，Redis被抢空后红包状态标记为已领完，MySQL侧异步落账。这套"热Redis冷MySQL"的分层，跟秒杀是同一个套路，但红包对账的要求让冷层的校验更严格。

## 坑与面试：红包特有的三个坑
**坑1：浮点精度。** 这个坑要命，10块钱对不平是真金白银的损失。 金额计算用`double`会出尾差，10块分10个可能分完是9.999999。必须全程`BigDecimal`，且设置`RoundingMode.DOWN`，最后一个兜底拿剩余。这个坑写代码时必踩，面试里主动提出来是加分项。

**坑2：超时退回。** 真坑。红包24小时没抢完，剩余金额要退回发红包的人。实现：定时任务扫描过期红包，把Redis剩余金额加起来退回；或者用延迟队列，每个红包发一个24小时的延迟消息，到期时处理。退回的金额要和抢到的对账，不能退错。

**坑3：账务对账。** 抢到的总金额 + 退回的金额 必须恒等于 发红包的总金额。这个恒等式就是对账的判据——每天跑一次，不等就是出事了。把"金额守恒"作为核心校验，比人肉查日志靠谱得多。

**面试官会怎么问：**

**Q1：红包金额怎么拆，才能保证不出现最后一个没得抢？**

> 用二倍均值法：每次从0到"剩余金额÷剩余个数×2"之间随机取一个值，最后一个拿剩余全部。这个上限设计保证前几个不会把金额分光，每个红包都在均值附近波动，既随机又均衡。

**Q2：抢红包的并发怎么保证不超抢？**

> 两种方案：一是金额预拆到Redis List，抢的时候LPOP弹出一个，单命令原子，天然不超抢；二是抢的时候用Lua脚本边算边扣。方案一简单且快，红包个数特别大才用方案二。另外用SADD记录已抢用户，拦一人多抢。

**Q3：为什么用BigDecimal不用double？**

> double是浮点数，二进制无法精确表示0.1这类十进制小数，累加会产生尾差。红包金额对账要求严格等于总金额，必须用BigDecimal，配合RoundingMode控制舍入，最后一个兜底拿剩余，分毫不差。

**Q4：红包抢完没抢完的怎么退回？**

> 定时扫描或延迟队列：每个红包发24小时延迟消息，到期检查剩余金额，退回发红包的人。退回金额加已抢金额必须等于发红包总金额，用这个恒等式做对账判据。

再往深一层看，红包和秒杀虽然在技术上相似，但业务语义完全不同：秒杀是"抢不到就算了"，红包是"人人有份还要算对账"。所以红包系统对一致性的要求比秒杀高一个量级——秒杀超卖顶多补发，红包账对不平是要赔钱的。这也是为什么红包方案里"金额守恒"永远是最高优先级的校验，任何一次抢、任何一笔退回，都不能打破"已抢+退回=总额"这个恒等式。面试官如果追问"红包和秒杀的本质区别"，从这个角度答，比背方案更有区分度。

## 带走清单
带走清单四条：金额拆分用二倍均值法，上限"剩余÷个数×2"，最后一个兜底，全程BigDecimal防尾差；并发抢用"预拆List + LPOP"，单命令原子不超抢，SADD拦一人多抢；先抢后入账要最终一致，消费重试+定时对账补账；金额守恒是红包对账的核心判据，已抢+退回=总额，每天对一次。
