### （2）自然人信息校验规则（V2.007新增）
需要新增以下校验逻辑：

```java
/**
 * 自然人信息校验
 * 1. 自然人国籍代码、证件类型、证件号码应当同时为空或同时不为空
 * 2. 证件类型与国籍代码的匹配校验
 * 3. 购买方自然人标志与自然人信息的关联校验
 */
public void validateNaturalPersonInfo(InvoiceUploadDTO dto) {
    // 规则1: 三字段同时为空或同时不为空
    boolean hasAll = StringUtils.isNotBlank(dto.getZrrgjDm()) 
                  && StringUtils.isNotBlank(dto.getZrrzjlxDm())
                  && StringUtils.isNotBlank(dto.getZrrzjhm());
    boolean hasNone = StringUtils.isBlank(dto.getZrrgjDm()) 
                   && StringUtils.isBlank(dto.getZrrzjlxDm())
                   && StringUtils.isBlank(dto.getZrrzjhm());
    if (!hasAll && !hasNone) {
        throw new BizException("自然人国籍代码、证件类型、证件号码应当同时为空或同时不为空");
    }
    
    // 规则2: 证件类型与国籍匹配
    validateIdTypeAndNationality(dto.getZrrzjlxDm(), dto.getZrrgjDm(), dto.getZrrzjhm());
    
    // 规则3: 自然人标志校验
    if ("Y".equals(dto.getGmfzrrbz())) {
        // 自然人标志为Y时的校验逻辑
        if ("201".equals(dto.getZrrzjlxDm())) {
            // 居民身份证: 购买方纳税人识别号必须与证件号码一致
            if (!dto.getGmfnsrsbh().equals(dto.getZrrzjhm())) {
                throw new BizException("居民身份证时，购买方纳税人识别号必须与证件号码一致");
            }
        }
    } else {
        // 自然人标志不为Y时，自然人信息字段必须为空
        if (hasAll) {
            throw new BizException("购买方自然人标志不为Y时，自然人信息字段必须为空");
        }
    }
}
```

### （4）代开关键词阻断校验（V4.003新增）
```java
/**
 * 代开关键词阻断校验
 * 对受票方名称、发票备注、附加要素信息进行校验
 * 若包含"代开"、"代理"、"开发票"、"QQ"、"微信"、"钉钉"等关键词，阻断开票
 */
private static final List<String> BLOCKED_KEYWORDS = Arrays.asList(
    "代开", "代理", "开发票", "QQ", "微信", "钉钉"
);

public void validateBlockedKeywords(InvoiceUploadDTO dto) {
    // 检查购买方名称
    checkKeywords(dto.getGmfmc(), "购买方名称");
    // 检查备注
    checkKeywords(dto.getBz(), "备注");
    // 检查附加要素
    if (dto.getFjysList() != null) {
        for (FjysDTO fjys : dto.getFjysList()) {
            checkKeywords(fjys.getFjysz(), "附加要素值");
        }
    }
}

private void checkKeywords(String content, String fieldName) {
    if (StringUtils.isNotBlank(content)) {
```

### （5）差额征税校验规则变更（V4.000调整）
```java
/**
 * 差额征税校验 - V4.000调整后规则
 * 1. 差额征税类型代码非空时，明细行只能一行，不允许折扣行
 * 2. 全额开票(01): 0 <= 扣除额 <= 含税金额
 * 3. 差额开票(02): 0 < 扣除额 <= 含税金额
 * 4. 商编校验: 必须在《建筑服务差额商编表》中，或通过原差额征税业务授权
 * 5. 税率校验: 按差额商编表中的税率/征收率校验
 * 6. 扣除凭证清单校验: 全额开票扣除额为0时无需填写，否则必填；差额开票必填
 */
public void validateDifferentialTax(InvoiceUploadDTO dto) {
    String cezslxDm = dto.getCezslxDm();
    if (StringUtils.isBlank(cezslxDm)) {
        return; // 非差额发票，跳过
    }
    
    // 明细行只能一行
    if (dto.getFpmxList().size() > 1) {
        throw new BizException("差额征税发票明细只能有一行");
    }
    
    FpmxDTO mx = dto.getFpmxList().get(0);
    BigDecimal kce = mx.getKce() != null ? mx.getKce() : BigDecimal.ZERO;
    BigDecimal hsje = mx.getHsje();
    
    if ("01".equals(cezslxDm)) {
        // 全额开票: 0 <= 扣除额 <= 含税金额
        if (kce.compareTo(BigDecimal.ZERO) < 0 || kce.compareTo(hsje) > 0) {
            throw new BizException("全额开票扣除额应在0到含税金额之间");
        }
        // 扣除额为0时无需扣除凭证清单，不为0时必填
        if (kce.compareTo(BigDecimal.ZERO) != 0 && 
            (dto.getCecckList() == null || dto.getCecckList().isEmpty())) {
            throw new BizException("全额开票扣除额不为0时，必须填写扣除凭证清单");
        }
    } else if ("02".equals(cezslxDm)) {
        // 差额开票: 0 < 扣除额 <= 含税金额
        if (kce.compareTo(BigDecimal.ZERO) <= 0 || kce.compareTo(hsje) > 0) {
            throw new BizException("差额开票扣除额应大于0且不超过含税金额");
        }
        // 必须填写扣除凭证清单
        if (dto.getCecckList() == null || dto.getCecckList().isEmpty()) {
            throw new BizException("差额开票必须填写扣除凭证清单");
        }
    }
    
    // 商编校验
    validateDifferentialTaxCode(mx.getSphfwssflhbbm(), cezslxDm);
    
    // 扣除凭证清单校验
    if (dto.getCecckList() != null && !dto.getCecckList().isEmpty()) {
        validateDeductionVoucherList(dto.getCecckList(), cezslxDm);
    }
}
```

### 场景分析
```
场景1: 部署后，开一张新发票
  → 主表写入 eli_invoice_main ✅
  → 扩展表写入 eli_invoice_main_ext ✅
  → 正常 ✅

场景2: 部署后，查询一张旧发票（部署前已存在的）
  → 主表有数据 ✅
  → 扩展表无数据 ❌（部署前没有这张表）
  → 如果代码用 INNER JOIN → 查不到数据 → 🔴 业务异常
  → 如果代码用 LEFT JOIN → 查到主表数据，扩展字段为NULL → ✅ 正常

场景3: 部署后，对旧发票发起红冲
  → 需要读取原蓝票的扩展信息
  → 旧蓝票无扩展记录
  → 如果代码假设扩展记录一定存在 → 🔴 NPE异常
  → 如果代码做空值判断 → ✅ 正常

场景4: 部署后，旧代码与新数据库共存（灰度期间）
  → 旧代码不查询扩展表 → ✅ 正常
  → 新代码查询扩展表（可能为空）→ 需做空值判断
```

### 2.4 🔴 部署顺序 — 风险：高（人为操作风险）
```
❌ 错误顺序: 先发代码 → 再执行DDL
   → 新代码查询不存在的表 → SQLException → 线上故障

❌ 错误顺序: 同时发代码和DDL
   → 时序不可控 → 可能出现表不存在的情况

✅ 正确顺序: 先执行DDL → 验证表创建成功 → 再发代码
   → DDL执行后，新表为空，旧代码不受影响
   → 新代码部署后，开始写入扩展表
   → 旧发票查询时扩展表为空，LEFT JOIN + 空值判断 → 正常
```
